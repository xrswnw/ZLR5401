0. 一页结论

  • 当前一次完整开锁测试需要「1×CONFIGURE + m×ADD + 1×START + 轮询QUERY/GET_EVENT + N×CONSUME_SOFT」，m 为硬标签数（1~16），N 为软标数。标签多时命令数线性增长。
  • 协议层流式拼帧已支持单帧最长 1024B data（PROTO_MAX_DATA=1024，字节级重组，跨 HID report 拼帧无障碍）→ "一条命令全带"在协议层完全可行，仅受上位机是否拆 report 发送约束。App_Locker.h 中"单帧受 56B 限制"注释已过时。
  • 固件 App_Locker_Configure() 内部即是"清单全量重建 + 置状态"的原子入口，单命令合并无需改动 App_Locker.c 状态机本体。
  • 已识别 6 个测试注意点/潜在坑（见 §8），其中 CONFIGURE 会清空已有清单 与 事件环形缓冲仅 8 条、满则丢最旧 对测试影响最大。

3. 一次完整开锁测试的命令时序（现状，以上位机视角）

帧格式：53 77 addr(1) 00 len(2) FC=0D data... CRC32(4) ｜ len = 1 + dataLen + 4（小端）

1CONFIGURE
建立结账任务（必发，会清空旧清单） —— 设 softCount=N；hardCount 字段只做上限预检。
53 77 xx 00 0B 00 0D 01 02 00 03 00 CRC32  ← hardCnt=2(预检), softCnt=3
响应 01 00。固件：App_Locker_Configure (App_Locker.c:108) → 状态 LOCKER_CONFIGURED。若当前忙 → 01 01 BUSY，需先 CANCEL。
2ADD ×m
逐条追加硬标签 EPC（m = 硬标签数，1~16 条，每条一条命令）
53 77 xx 00 0A 00 0D 02 0C E2 00 34 12 ... (12B EPC) CRC32  ← 追加 12 字节 EPC
每条响应 02 00。固件：App_Locker_AddTag (App_Locker.c:128)。EPC 超 12B 被截断到 12B。
3START
激活任务：UHF 上电 + 开扫 + 起保持窗口
53 77 xx 00 06 00 0D 03 CRC32
固件：App_Locker_Start (App_Locker.c:142) —— App_UHF_Open()（非 READY 时）→ App_UHF_Inventory() → 窗口 = 2min + (m-1)×30s → ERR 灯灭。此后磁块"可开锁"。
4轮询
测试观察阶段 —— 轮询 QUERY + GET_EVENT（推荐间隔 ≤500ms，见坑②）
QUERY: 53 77 xx 00 06 00 0D 05 CRC  →  05 00 state hm(L) hm(H) sc(L) sc(H) su(L) su(H)
GET_EVENT: 53 77 xx 00 06 00 0D 07 CRC  →  07 00 evtCode epcLen epc.. hm(2) su(2) sc(2) hc(2) 或 07 03(无事件)
本阶段固件主循环自动运行：locker_process_configured (App_Locker.c:188) 每 tick 保持扫描、取标签、比对、驱动升降（见 §5）。
5CONSUME×N
软标阶段（仅 softCount>0 时）—— 上位机模拟解码完成，逐次上报消耗
53 77 xx 00 06 00 0D 06 CRC  →  06 00
固件：App_Locker_StopDecode (App_Locker.c:169)，softUsed+1；softUsed==softCount 时置 DONE + 5s 倒计时。 固件侧不主动检测软标，完全靠这条命令驱动（坑③）。
6CANCEL
结束 / 随时中止（DONE 5s 后会自动回 IDLE，CANCEL 用于提前或超时场景）
53 77 xx 00 06 00 0D 04 CRC  →  04 00
固件：App_Locker_Cancel (App_Locker.c:160) —— UHF 停扫 + lower_lock() 磁块回降 4800 微步 + 回 IDLE。

命令总数 = 2 + m + 轮询(若干) + N。 例：m=2 硬标签 + N=3 软标 ≈ 7 条命令 + 轮询；m=16 时 ADD 一项就要 16 条。

6. 事件上报机制与时间参数

事件环形缓冲 (App_Locker.c:29-67)

  • 容量 8 条；满时丢弃最旧再压入（evr_push L52-55）。
  • 每条事件快照：code + EPC(≤12B) + 四个计数字段 + 时间戳。
  • 上位机 GET_EVENT 一次取 1 条，取完为止；无事件回 LOCKER_ERR_NO_EVENT=3。
  • 没有主动推送——纯轮询拉取模型。

事件码表

码事件触发时机
0MATCH_OK硬标签命中清单
1MISMATCH读到非清单 EPC
2HARD_DONEm==n 全解锁
3SOFT_USEDCONSUME_SOFT 每次
4TIMEOUT保持窗口到期
5DONE软标用尽 / 无软标直达
6FAULTUHF 链路故障

时间与步数参数 (App_Locker.h:68-72)

宏值含义
BASE_HOLD_MS120 s基础开锁保持窗口
EXTRA_PER_TAG_MS30 s每多 1 硬标签加时
DONE_IDLE_MS5 sDONE 停留后回 IDLE
STEP_RISE4800 µ步升起步数 (dir=0)
STEP_LOWER4800 µ步回降步数 (dir=1)

几何参考（记忆库）：当前 1/2 微步 = 400 步/转，下→上行程实测 ≈4287 微步。4800 步略超行程，靠机构上限位截断——行程开关无停转保护（已知暂不实现）。

升降动作链

rise_lock/lower_lock → App_Stepper_Move (App_Stepper.c:255)： FAULT 位置位时先 drv8434s_clear_fault 清障再启步（对应上电首驱 nFAULT 误停问题）→ TIM4 硬件 STEP 脉冲 + S 型加减速 → 运行中监测 FAULT/DIAG2(堵转)/nFAULT 引脚，任一触发即停转并回 IDLE。

7. "一条命令控制"提案（未实施，待确认）

提案 LOCKER_SUB_ONE_START (0x08) — 一键开锁

53 77 xx 00 len(2) 0D 08 softCntL softCntH tagCnt [epcLen1 epc1..] [epcLen2 epc2..] ... CRC32
  • 语义 = CONFIGURE + ADD×m + START 三合一。内部直接调 App_Locker_Configure(items, tagCnt, softCnt) → App_Locker_Start()，App_Locker.c 状态机零改动。
  • 容量核算：data = 4 + m×(1+12B)，m=16 时 212B < PROTO_MAX_DATA=1024 ✓。
  • 帧长 223B > HID 单 report 63B 有效载荷 → 上位机拆 4 个 report 连续发送，固件流式解析器（ProtoParseByte (App_CustomProtocol.c:74)）天然支持跨 report 重组，传输层与固件协议层均无需改动。
  • 待确认 ①：非 IDLE 收到 0x08 → 回 BUSY（保守）或隐式 Cancel 重建（更"一键"）？当前倾向 BUSY。
  • 待确认 ②：旧命令 CONFIGURE/ADD/START 保留作调试路径，与 0x08 共存。
  • 改动面：仅 App_CustomProtocol.h（+1 宏+注释）与 App_Dispatch.c:699（+1 case）；上位机 SwComForTool 增加发送封装（需确认其 HID 写函数是否已支持 >63B 自动拆包）。

8. 测试注意点 / 已识别坑（现状）

#问题位置影响与建议
坑①CONFIGURE 会清空已有清单：hardCount 字段只作预检不写入，清单必须靠后续 ADD 重建 App_Dispatch.c:704-725 下发顺序错误（CONFIGURE 发在 ADD 之后）会静默清掉清单；测试脚本必须严格 CONFIGURE→ADD→START 顺序
坑②事件缓冲仅 8 条，满丢最旧，无主动推送 App_Locker.c:29,52 GET_EVENT 轮询间隔过长会漏事件（尤其 MISMATCH 高频时）；建议 ≤500ms 轮询
坑③软标消耗完全由上位机驱动（CONSUME_SOFT），固件不主动检测软标 App_Locker.c:249-259 测试时必须模拟 N 次 CONSUME_SOFT，否则 SOFT_DECODE 只能靠窗口/超时退出；注意 SOFT 态 holdDeadline 已清零，实际只能 CANCEL 退出
坑④每次 MATCH_OK 刷新保持窗口（2min+(m-1)×30s 重新计算） App_Locker.c:216-219 逐个放置标签可持续延长窗口；若测试期望"固定窗口"语义，实际行为不同
坑⑤头文件 LOCKER_UNLOCK_HOLD=2 状态未实现，匹配保持嵌在 CONFIGURED 态 App_Locker.h:41 上位机 QUERY 看到的 state 不会出现 2；文档/上位机若按 5 态解析会错位
坑⑥磁块升降依赖 DRV8434S；持续 FAULT 时表现为"匹配了却不升起"（Move 内部仅清障重试一次） App_Stepper.c:255-266 结合既有记忆：上电首驱曾出现 nFAULT 间歇误停（0-21 步，~50%），已由 seek_phase 重试缓解；若测试偶发"不升起"，先 MOTOR_CMD_QUERY 查 fault 寄存器

9. 协议层关键事实（与"一条命令"可行性直接相关）

  • PROTO_MAX_DATA = 1024 (App_CustomProtocol.h:14) —— 帧长度字段 16bit，长度校验上限 1024+5。
  • 解析器 ProtoParseByte 是逐字节状态机：0x53→0x77→addr→00→len(2)→payload→CRC32，与 HID report 边界完全解耦——一个逻辑帧可由任意多个 report 拼出。
  • USB 传输层：HID report 64B（首字节 report id 0x01 剥离后 63B 有效）(App_Usb_Transport.c:98, App_Usb_HL.h:33)。上位机 SwComForTool 侧是否已实现">63B 帧自动拆 report 连发"是单命令方案的唯一未确认点。
  • App_Locker.h:20-22 注释"上位机单帧受 HID 56B data 限制"与实际协议能力不符，属陈旧文档，实施单命令方案时应一并修正。
