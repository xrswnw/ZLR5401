2. 更新方案（主机客户端 zlr_updater）

闭环流程完全基于 Boot 侧既有协议，不改变设备端时序，仅由主机驱动：

  1. EN_BOOT (FC_EN 0x02)：App→写 UPG→软复位换固件到 BOOT。等待重枚举+握手 layer=0。
  2. UPGRADE_START (0x03)：16B 头(Size/CRC/FwVer/BindVerify)+校验级别；Boot 整区擦除。结果码校验 (RESULT_OK=0)。
  3. FW_DATA (0x04)：按 48B 分块；帧 = seq(2)/addrOffset(2)/data；带块级重试（容忍瞬态丢响应/丢帧，设备幂等写）。
  4. UPGRADE_VERIFY (0x05)：Boot 对整区重算 CRC + 尺寸 + 向量校验，返回 0 才继续。
  5. UPGRADE_EXEC (0x06)：两步提交（RUN 最后写）→ 软复位回 App。握手 layer=1。
  6. upgradeCount 校验：升级前后读取，要求 after = before + 1，作为“真实提交落地”的强证据。

全套脚本：Agent/Round_009/update/（conf / zlr_updater / fw_crc / fault_inject / loop_run）。复用 Agent/Round_008/test/zlr 的 HID/frame/crc32 基础设施。

3. 测试期间发现并修复的一个固件健壮性问题

3.1 现象

U6（重复/乱序发送）用例在固件改动前失败：DATA 块在 #1111 offset=0xD050 处被设备回 DATA_ADDR_ERR(3)，后续所有块被拒。

3.2 根因

原 Boot_Dispatch.c 的 DATA 处理以累计字节数计进度：

  • if (State != IAP_ERASED) → DATA_ADDR_ERR（[Boot_Dispatch.c:117]）；
  • 每写一块 Written += dataLen，一旦 Written >= FwSize 即置 IAP_DATA_DONE（:160-162）。

因此当主机因现场不稳而对同一块重复投递时，`Written` 被重复累加，可能在整个镜像尚未投递完时就越过 `FwSize`，随后所有合法块都被当作非 `IAP_ERASED` 而拒绝。这是写入进度测量方式在“重复/重传”输入下不具幂等性的固件缺口。

3.3 修复

将进度改为“最高已覆盖地址”（max-covered）计数，使重复/乱序重发幂等：

/* 以最高已覆盖地址(counting)计进度，使重复/乱序重发幂等 */
uint32_t covered = target + dataLen - APP_FLASH_ORIGIN;
if (covered > g_sIap.Written) g_sIap.Written = covered;
if (g_sIap.Written >= g_sIap.FwSize) g_sIap.State = IAP_DATA_DONE;

VERIFY 处的完成判据 Written == FwSize（:176）在该方案下依旧正确成立。修改仅此一处，位于 Bootloader/src/Boot_Dispatch.c。已重新编译烧录 BOOT，全量回归通过（§4、§5）。

8. 结论与建议

结论

  • HID 闭环更新链路稳定可靠：20 轮连续完整更新零失败，提交计数严格 +1。
  • 固件容错在所有可预见的失败/中断场景下都满足“失败则停留 BOOT、可重试重写”的核心要求（F1–F7、U1–U7 全过）。
  • 过程发现并修复 1 处真实固件健壮性缺口（DATA 进度累计不幂等，详见 §3），修改后无副作用、全量回归通过。

建议（可选，非阻塞）

  • 可考虑让主机在 START 后发送第 0 块时带一个“同步/复位 IAP 会话”意图，进一步缩短异常后的恢复路径（当前已足够，仅为锦上添花）。
  • 如现场允许，可将块尺寸由 48B 提至 HID 数据区上限 52B，减少总帧数约 8%（传输时间相应缩短）。
  • 升级前建议主机先读一次 upgradeCount 并与上位机侧记录比对，作为“已烧录版本/固件标识”的附加校验手段。
