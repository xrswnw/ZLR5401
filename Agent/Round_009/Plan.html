2. 现有 HID 更新流程审查（结论先行）

已通读 Bootloader 与 App 相关源码，流程与布局如下。

2.1 Flash 布局（Boot_Config.h:29-37）

区域地址大小说明
BOOT0x0800000022K升级引导 + USB HID
PARAM0x080058002K(用512)参数区（UPG/RUN 标志等），升级不擦除
APP0x08006000232K应用固件，升级目标

2.2 完整更新时序（当前实现）

App 收到 FC_ENTER_BOOT(0x02)→ 写 UPG + 复位→ Boot 识别 UPG → 常驻等待→ FC_UPGRADE_START(0x03) 擦除→ FC_FW_DATA(0x04) 逐块写→ FC_UPGRADE_VERIFY(0x05) CRC/向量→ FC_UPGRADE_EXEC(0x06) 两步提交+复位→ Boot 重校验 → 跳 App

2.3 关键实现点（file:line）

环节位置行为
App 进升级App_Dispatch.c:59-75写 deviceStatus=UPG → ParamSave → ACK + 50ms → NVIC_SystemReset → 跳 Boot
Boot 驻留判断Boot/main.c:173,178stayInUpdate = (deviceStatus==UPG)；为真则进 while 无限轮询（永不超时）
IAP 会话续时间窗Boot/main.c:185-186一旦 g_sIap.State != IAP_IDLE，持续刷新冷启动 2.5s 窗口 → 中途断电*不致误跳
START(0x03)Boot_Dispatch.c:55-11316B 头（FwSize/FwCrc/FwVer/BindVerify，LE）+ 可选校验级；按需擦页并逐页喂狗
DATA(0x04)Boot_Dispatch.c:115-169[seq(2) | addrOffset(2) | data]；按 addrOffset 写 4B 字；无块内 CRC（帧级 CRC 兜底）
VERIFY(0x05)Boot_Dispatch.c:171-228size → CRC32 整区 →(MID)MSP/Reset 向量 →(FULL)绑定；成功才置 VERIFY_OK
EXEC(0x06)Boot_Dispatch.c:230-265需 VERIFY_OK；两步提交：先写 appCrc/appSize/count，最后才写 RUN（提交点）→ 复位

EXIT_BOOT(0x09)Boot_Dispatch.c:298-352同样校验后清 UPG→RUN → 复位跳 App；失败不复位

*"断电"在本测试中不可真断电，用 FC_RESET(0x08) 软复位模拟中断场景。

3. 容错性审计：失败为什么能停留在 BOOT

需求 #3（纵使更新失败也停留 BOOT 可继续更新）在当前固件已具备，四条防线相互独立：

  1. UPG 粘滞：START→VERIFY 全程不改 deviceStatus，仍为 UPG → Boot 常驻（main.c:178 无限轮询）。
  2. IAP 续窗：IAP 会话中每次轮询不断刷新 2.5s 冷启动窗口（main.c:185-186），中途失败/重发不会误跳 App。
  3. 两步提交：RUN 是最后写入（EXEC Step2, Boot_Dispatch.c:260）。提交前任何中断 → 仍是 UPG，主机只需重发 START+DATA+VERIFY。
  4. 跳前复核：JumpToApp / EXIT_BOOT 在跳 App 前对 App 区做 MSP/向量/CRC 复核；写入损坏则拒绝跳转、死后循环在 BOOT（main.c:196-202）。

结论：固件侧已满足"失败留 BOOT"。本测试的价值在于用真实 HID 链路验证这四条防线，并把"失败注入→确认留 BOOT→重试成功"纳入自动化。

本轮我选定的更新方案（需求 #4）：不重写 Boot 升级协议（已足够健壮），专注补齐主机侧闭环与验证——即写一个能自动"进 Boot→上传→校验→提交→确认回到 App→统计升级计数"并带故障注入能力的驱动器。理由：改动最省、风险最低、且能直接论证需求 #3。

4. 测试方案总体设计

4.1 选定的主机驱动器流程（单轮）

握手探测(App? Boot?)→ 记 upgradeCountbefore→ App→BOOT (ENTER_BOOT)→ 等重枚举 + 握手(layer=0)→ START(擦+记录)→ DATA 分块写(≤52B/块)→ VERIFY→ EXEC(两步提交+复位)→ 等重枚举 + 握手(layer=1)→ 记 upgradeCountafter = before+1 ✔

4.2 关键决策与理由

决策选择理由
校验级别MID（默认，验证非 0 时显式传 0x02）CRC + MSP/Reset 向量已足够；FULL 因绑定与同批固件可重复一致，做一轮附加即可，避免头 16 字节局促
DATA 块大小48B（4 对齐、≤52 上限）USB 单帧 data≤56，扣 FC_FW_DATA 4B 头 → ≤52；取 48 留余量且按 4B 对齐，减少字写入边界处理
升级投递物复用 Build/app.bin（build_app.sh 产物）即线上 OTA 二进制，与 gen_firmware.sh 口径一致；无需新增构建
成功判据握手 layer 从 0→1 + upgradeCount 严格 +1upgradeCount 由 EXEC 递增并持久化，是"校验+提交+复位+重新运行"的强证据，优于只看能握手
重枚举策略沿用 Round_008 hid_link._reopen 轮询模式App/Boot 同 VID:PID，靠握手 layer 区分固件身份
环境仓库 .venv（python + hid）Round_008 已验证，无需新增依赖

6. 关键难点：固件 CRC 算法必须与 Boot 精确一致

最高风险点。Boot 端 VERIFY 用 Crc32Calc(APP_FLASH_ORIGIN, FwSize)（Boot_Dispatch.c:184）与主机上报 FwCrc32 比对；START 头里 FwCrc32= data[4..7] LE。若主机算出的 CRC 与 Boot 的 Crc32Calc（Boot_Param.c:8-20，bit-reflected-not 变体）不一致，VERIFY 必然恒失败。

  • 帧校验用 MPEG-2（zlr/crc32.py），不同于固件镜像 CRC —— 二者必须分开实现。
  • 计划：先以 Crc32Calc 源码为准实现 fw_crc.py，并在脚本内加自检：预先对已知字节串比对 Python 与 Boot 参照值（若不确定，可用校验已知固件的 VERIFY 实际返回值校准）。
  • 这是脚本正确性第一道闸门，放在 loop_run 前置自检。
附加一致性校验：MID 校验还检查 MSP/Reset 向量。app.bin 首位即 MSP（应 0x2000_0000 掩码），[4] 为 Reset 向量（须落于 APP 区）。主机可在上传前静态断言 app.bin 前 8 字节满足，提前拦截"烧错文件"型失误。

7. 测试用例矩阵

7.1 基线：20 次完整更新（需求 #3 主判据）

轮要点期望
1–20每轮从头 ENTER_BOOT→上传→VERIFY→EXEC→重回 App，判 upgradeCount+1 且 layer=120/20 通过；任一轮失败即整体 FAIL

7.2 故障注入（验证"失败留 BOOT 可重试"）

#注入手法期望（固件防线）
F1DATA 中途丢 1 帧（跳序/不响应）→ 重发该块继续帧级 CRC 不匹配被静默丢弃，状态不破坏；重发后成功（防线 1/2）
F2DATA 发损坏块（帧 CRC 错）设备丢弃不写；重发正确块继续
F3上传错 CRC 的固件** → VERIFY 返回 VERIFY_CRC_MISMATCH设备留在 BOOT、仍 UPG；重发 START 正确固件后成功（防线 1/3）
F4VERIFY 通过后、EXEC 前发送 FC_RESET（模拟提交前中断）复位仍 UPG → 停留 BOOT；完整重跑恢复（防线 2/3）
F5擦除后（START 完成）不写数据即重置仍 UPG 留 BOOT；重发 START 可重写（防线 2）
F6EXIT_BOOT 在损坏镜像下 → 拒绝复位返回错误且不跳 App，留 BOOT（防线 4）
F7EXEC 成功后立即软复位，验证"新固件已持久"第二次启动直接回 App（RUN 已提交）

7.3 现场异常：USB 不稳 / 链路抖动（新增）

模拟现场真实 USB 扰动，覆盖需求 #3 的链路层面，而不只是命令层面。每项先注入扰动、随后用正确固件完整重跑确认可恢复。

#扰动手法期望
U1DATA 阶段随机丢响应帧（部分块不发/不发不求，按块超时）块超时→重发同 seq；最终 VERIFY 过、升级成功
U2块间随机插入 10~500ms 延迟 / 主机假死不受快慢影响，慢速上传仍完整（设备无限等待 UPG）
U3升级中途中止 USB 重新枚举（close+reopen，模拟现场拔插/枚举抖动）重枚举后仍在 BOOT(UPG)；重启 START 重跑成功
U4响应超时（设备不回应某块，主机等超时后重发）超时重试而非误判；重发后继续，最终成功
U5连续快速批量发包（无间隔，压迫 USB/批量速率）满速写入不丢序、VERIFY 通过（压力测试）
U6乱序/重复发包（某块发两次、或提前发下一块）末尾以 seq+offset 确定性写入，最终仍 VERIFY 通过
U7固件尺寸边缘：非 48 倍剩余块 / 超长（>app 区）边界末块正确落位；超长被 START 拒(UPG_NO_SPACE)留 Boot

**F3 注入在主机侧对 app.bin 字节做局部翻转并同步改 FwSize/Crc，但不改 MSP/向量，确保命中 CRC 分支而非向量分支，定向验证 CRC 防线。

每项注入都设置恢复路径：注入导致失败后，脚本继续用正确固件完整重跑一遍，证明"失败后可重试直至成功"。

11. 风险评估

风险等级缓解
固件镜像 CRC 与 Boot 算法不一致 → VERIFY 恒败高§6 前置自校 + 依据源码 Crc32Calc 实现
