0. 执行摘要

本轮按 Plan.html 执行了 ZLR5401 全系统测试: P1 协议层 / P2 基础功能 / P3 电机 / P4 UHF / P5 AM / P6 Locker 业务(含真实标签+电机升降) / P7 IAP 升级全链(含四级校验注入) / P8 稳态压力, 全程 USB + JLink 双通道, 每个缺陷走 FAIL→定位→修复→重烧→回归 闭环。共修复 7 个固件缺陷 (BUG#1~#7) 与若干测试框架问题, 终态 P1~P8 全绿 (P3 的 10 项 FAIL 为设计层已知行为, 已归入 P9 优化清单, 非缺陷)。

最重要的一条主线: P7 IAP "VECTOR 注入挂死"事件 — 表面现象是设备在升级校验注入时永久哑死, JLink 三次现场取证 (PC/寄存器/RAM 变量/SysTick 状态/FLASH 内容) 后层层剥开, 实为 三个独立缺陷叠加: Boot 兜底循环停 SysTick 后不自愈 (BUG#5) + USB TX busy 永久锁存 (BUG#6) + 测试框架校验级别枚举语义与固件相反导致垃圾固件被误 EXEC (BUG#7)。三处修复后 IAP 全链 32 用例 0 失败, 且设备具备 IAP 自愈能力 (无需 JLink)。

2. BugList — 缺陷修复闭环记录

BUG#1 P2 SELFTEST CLEAR 帧布局与协议文档不符

现象: CLEAR 子命令按文档布局 [cmd, maskL, maskH] 下发无效果。
根因: 固件 CLEAR 解析布局与文档不一致。
修复: 固件对齐文档布局。回归: B4d PASS (清后 errBits=0x0000)。

BUG#2 P5 USB TX >63B 截断 (AM 波形页丢数据)

现象: GET_WAVE_PAGE 53B data (64B 帧 = 2 个 HID 报文) 只回第一报文, 主机侧全部超时。
根因: STM32 USB PMA 单 IN 报文上限 64B (含 ReportID); 固件一次 UserToPMABufferCopy 整帧写入导致超长部分静默丢弃; 且片间等待 50ms 不足 (主机 hidapi 读周期 ~64ms), 提前 SetEPTxValid 被忽略并覆写 PMA 破坏在途分片。
修复: App_Usb_Transport.c TxDma 分片为 63B 片 + 片间 App_Usb_TxBusy 等待上限放宽至 1000ms。
回归: WAVE_PAGE 9 页 400 点全量回传一致 (P5 全绿)。

BUG#3 P6 LOCKER ADD 长度校验逻辑错误

现象: 短帧 / 超长 EPC 的 ADD 被静默接受, 读到垃圾数据。
根因: 校验条件 2+epcLen>dataLen && epcLen>MAX — 应为 ||, 两条件同时才拒绝。
修复: App_Dispatch.c 改为 ||。回归: L4 (ADD 超 16 条/超长 EPC → LOCKER_ERR_PARAM) PASS。

BUG#4 P7 IAP FW_DATA 偏移字段 u16 装不下真实固件

现象: IAP 对 78KB 固件静默失效 (所有 FW_DATA 无编码)。
根因: addrOffset 为 u16 (≤65535), 而 App 区已扩到 232KB — Boot_Config 扩容时未同步本字段。
修复: Boot_Dispatch.c 扩为 u32 (帧 data[2..5]), Protocol/Boot_Protocol.html 同步更新。
回归: I5e 78371B / 240B 分片 / u32 偏移全量上传 + VERIFY + EXEC + App 重启成功; 升级计数 +1。

BUG#5 P7 Boot 兜底循环停 SysTick 后不自愈 → 协议响应无限自旋死模式

现象: App 区无效时设备落入永久哑死 — USB 枚举正常但任何帧无响应; JLink 取证: PC=WaitEp1Ready 自旋, SysTick CTRL ENABLE=0, ms 计数器冻结在 2500 (=BOOT_TIMEOUT_MS)。
根因链: Boot 主循环超时退出 → SysTickHl_Stop() → JumpToApp() 失败 (App 无效) → 落入 while(1){Proto_Poll();…} 兜底 — 但 SysTick 未重启。此时任何协议响应的 WaitEp1Ready 自旋以 (GetMs()-t0)<50 为唯一退出条件, ms 冻结 → 单次调用永不返回。
修复: ① main.c 兜底循环前 SysTickHl_Init() 重启; ② WaitEp1Ready 增加 4e6 次硬迭代上限 (~0.3s @72MHz), 不依赖 SysTick (Boot+App 同步)。
回归: 修复后 App 无效时设备在兜底循环正常应答 (layer=0 稳定), 注入轮 I6C-s PASS。

BUG#6 P7 Boot USB TX busy 永久锁存, 响应静默丢弃

现象: 单次 IN 完成中断丢失 (主机侧竞态) 后, g_boot_usb_tx_busy 与 EP_TX_VALID 永久锁存, 之后所有响应在 Boot_Usb_HL_Transmit 入口 return — 设备主循环活着但永不应答 (I6C 会话 VERIFY 响应丢失的固件侧成因)。
修复: 记录 busy 置位时间戳, >200ms 强制回收 (SetEPTxStatus(ENDP1, EP_TX_NAK) 清 VALID + busy 复零) 后照发。
回归: IAP 全链重跑无响应丢失; 注入轮 I6C-x/e/s 全部正常应答。

BUG#7 P7 测试框架校验级别枚举与固件/文档语义相反 → 垃圾固件被误 EXEC

现象: I6C "VECTOR 注入" 表现为设备挂死, 其后所有用例超时 — 曾被误判为固件崩溃。
根因链 (JLink 三次现场取证 + RAM 参数块/FLASH 内容比对还原): 测试脚本 (沿用 Round_009 conf.py) 定义 MID=2/FULL=3, 而固件与 Boot_Protocol.html 均为 FULL=0/MID=1/BASIC=2。I6C 以 "MID"=2 下发, 实际是 BASIC — 跳过向量校验, 全零镜像 (MSP=0) 被 VERIFY 放行 → State=VERIFY_OK → I6C-x 的 EXEC (本意验证拒绝) 直接提交垃圾固件并复位 (参数页实锤: appCrc32=0x44113DD3=crc32(零镜像), 升级计数 +1)。复位后 USB 重枚举期间脚本旧句柄失效 → 后续全 TO; 复位后设备按设计驻留 Boot, 叠加当时旧固件的 BUG#5 → 死模式。
修复: 测试脚本枚举对齐文档语义 (0/1/2); I5j 升级计数读数加 layer 过滤 (陈旧回显干扰)。
回归: 终轮 I6C (VECTOR 注入 → VERIFY_VECTOR_INVALID) / I6D (BIND 注入 → VERIFY_BIND_FAIL) / I6E (IAP 自愈) 全 PASS, P7 32/0。
备注: 该事件同时暴露并推动了 BUG#5/BUG#6 与 Boot fault handler 死循环的修复 — 是本轮最有价值的测试用例。

附加修复 Boot fault handler 死循环 → 复位自愈

Boot 无 IWDG, HardFault/BusFault/UsageFault/MemManage 死循环 = 永久哑死 (只能 JLink/断电)。对齐 App 策略改为 NVIC_SystemReset(): 复位后 Boot 重新可响应, IAP 协议幂等可重试。注: 若 fault 立即复现会形成重启循环 — 已列入优化清单 (建议 fault 计数降级)。

5. P9 用户视角设计评审

5.1 开锁体验主线 (普通用户视角)

OneShot 全流程时序: 实测 PRECHK→IR_WAIT→…→HOLD→DONE 各阶段语义清晰、阶段码可查询 (GET_PROGRESS), 单指令完成整个开锁 — 对上位机集成者直观。但作为普通用户:

  • NO_IR 无放标提示: 光电门控等待窗内无标签时只有超时+错误码, 无灯语/蜂鸣主动提示 "请放标签" — 建议加等待窗内呼吸灯。
  • MISMATCH 红闪 3s: 时长够明确, 但红闪与 FAULT 红灯语可能混淆, 建议差异化频率。
  • maxHoldMs 双语义: 同一字段兼作 IR 等待窗与保持窗 — 实测两者节奏完全不同 (等待要短、保持要长), 用户无法分别调优 → 建议 #21 拆分字段。

5.2 灯语可懂性

7 稳态+5 闪显在协议层全部可控可回收; 但蓝通道缺失降级后存在撞色: 白 (R+G 合成) 与回零黄慢闪、手动态黄与 DONE 黄的辨识依赖频率而非颜色 — 普通用户可辨识度低。建议输出统一颜色语义表并优先用频率差异化 (已列人工观察清单)。

5.3 错误码自解释性 (上位机集成者视角)

  • ONE_ERR_x / LOCKER faultReason / SELFTEST 位图 三层错误体系分层合理, 实测排障 (本轮 7 个缺陷定位) 全程够用。
  • 缺口: IR (PC4) 传感器状态无直读命令 — NO_IR/门控类排障只能靠间接推断 (本轮台面 PC4 间歇高电平即受此限制); UHF 模块电压/天线状态无直读。→ 建议 #8。
  • 升级失败码 (VERIFY 四级 + SIZE/CRC/VECTOR/BIND 分码) 实测足以指导主机重试策略 — I6E 自愈流程验证了这一点。

5.4 升级体验

  • Boot 停留期 (UPG 驻留) 无 App 业务 — 用户感知为 "设备在线但不可用", 协议层有 layer 字段可判定, 可接受。
  • 工程现场痛点: SWD/JLink 重烧 App 后参数页记录的 appCrc32 不匹配 → 设备驻留 Boot 且 EXIT_BOOT 也被 CRC 检查拒绝 — 唯一恢复路径是完整 IAP 一轮 (本轮实测自愈成功) 或重写参数区。建议提供工程模式 (忽略 CRC 跳转 / 重置参数区)。→ 建议 #5。
  • EXEC 的两步原子提交 (先校验值后 RUN 标记) 掉电语义设计良好, 本轮注入测试验证了 "RUN 未写成则留 UPG" 的断电自恢复路径。

5.5 状态机视角

  • FAULT 出口窄 (仅 CANCEL) — 实测注入轮后均能干净回 IDLE, 安全性优先, 可接受; 但建议 FAULT 态可查询更细 faultReason 字段。
  • DONE 停留 5s + 保持窗 2min+30s/标签: 实测 UNLOCK_MULTI 稳定确认 3s/2 命中与节奏匹配; 长窗 (2min) 对无人零售场景合理。
