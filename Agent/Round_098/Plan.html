2.2 Boot 侧协议(IAP 升级链)

FC验证点
0x01 HANDSHAKE / 0x07 DEVICE_INFOBoot 身份标识(区别于 App)
0x03 UPGRADE_START擦除/空间检查(UPG_NO_SPACE/ERASE_FAIL)

3. P0 — 环境与基线 + 硬件自适应探测

步骤:
  1. ./backup.sh "Round_098 测试前全量快照" —— 任何修改前先落快照(遵循全局备份规则)。
  2. 干净构建 ./build_all.sh(含未提交改动) → 产物 ZLR5401_<ts>.hex;记录 elf/bin CRC 作为升级测试基准。
  3. ./flash_all.sh 全片烧录(Boot 0x08000000 + App 0x08006000), 复位运行。
  4. 存活探测: 5s 内握手 OK; DEVICE_INFO 回 ZLR5401_V1.0; SELFTEST QUERY 记录基线位图(期望 errBits=0, 若非 0 记录并归因); MotorQuery=IDLE; 60s 心跳无 IWDG 复位(时间戳单调)。
  5. 硬件自适应探测(产出"硬件在场表"决定后续用例集):
    • UHF: OPEN→INVENTORY×3 轮 → 记录"在场标签 EPC 列表"(有/无)。
    • AM: QUERY → 链路在/断。
    • 光电 PC4: 无直读命令, 经 OneShot 短窗间接判定(见 P6 用例 OS-1, 两种结果均为有效断言)。
    • 行程开关: SELFTEST QUERY switchErr + Homing ready 位。
    探测结果写 hw_presence.json: 有硬件→全用例; 无硬件→失败路径用例 + 其余 SKIP(记录, 不算 FAIL)。

编号用例期望

6. 挂死/崩溃诊断通道(JLink)

自动化"无响应>10s"时触发: JLinkGDBServer -device GD32F303RCT6 + arm-none-eabi-gdb 批处理 attach → 读 PC/LR/SP、HFSR/CFSR(HardFault 归因)、栈回溯定位调用链 → 落 diag_<ts>.txt 供 BugList 引用; 诊断后 halt→reset 恢复设备。

7. BUG 修复闭环(贯穿全程)

流程: FAIL → 最小复现(固定种子的重放) → 定位(响应帧分析/复现日志/JLink §6) → 修复(最小改动, 遵循工程注释与命名风格) → 重编译 → 重烧 → 该用例 + 关联用例回归 PASS → 受影响 phase 全量回归 → 记录 BugList。
BugList 字段: 编号 / 阶段-用例号 / 现象 / 根因 / 修复摘要(diff 行数) / 回归结果 / 关联风险。
边界纪律: 只修确认的缺陷(与协议文档/注释约定不符的行为); 协议语义、状态机设计、灯语方案等设计层面不动 —— 一律进 §P9 建议清单交用户决策。每 N 个修复做一次 git 提交(附 BugList 引用), 全程不改协议文档语义。

9. P9 — 用户视角设计评审大纲(终态产出)

以"什么都不懂的普通用户/上位机集成者"双视角评审, 输出进 Report.html:
  • 开锁体验主线: 一条 OneShot 指令的全流程时序是否直观? NO_IR 无放标提示(灯语/蜂鸣)是否可感知? MISMATCH 红闪 3s 够不够明确? 光电门控等待窗(maxHold 兼用)语义是否混淆?
  • 灯语可懂性(衔接 Round_011 需求): 7 稳态+5 闪显的普通用户可辨识度; 蓝通道缺失降级后的颜色撞色(如白→黄 vs 回零黄慢闪)是否会误导; 建议统一颜色语义表。
  • 错误码自解释性: ONE_ERR_x / LOCKER faultReason / SELFTEST 位图 —— 上位机排障是否够用, 缺哪些语义(如 IR 传感器状态无直读命令)。
  • 升级体验: Boot 停留期无 App 业务时的用户感知; 升级失败码是否可指导重试; EXIT_BOOT 后的状态恢复。
  • 状态机视角: FAULT 退出路径(CANCEL 唯一出口)是否窄; DONE 停留 5s 的合理性; 保持窗 2min+30s/标签 与实测节奏的匹配。
  • 协议一致性: 协议 HTML 文档 vs 实测行为 diff 清单(如 DEVICE_INFO 硬件名 C8T6 遗留)。
每条给出: 现状 → 合理性判定 → 具体优化建议(不改码, 供决策)。
