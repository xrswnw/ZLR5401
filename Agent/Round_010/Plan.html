1. 背景与需求

设备实际外设灯带为 RGB 三色（高电平点亮，无调光），可组合出 7 种亮色 + 熄灭 = 8 种状态： 红、绿、蓝、黄(红+绿)、青(绿+蓝)、紫/粉红(红+蓝)、白(红+绿+蓝)、灭。

当前固定逻辑仅为需求约定的两条：硬标签匹配 → 绿灯常亮 + 升起开锁；失配 → 红灯闪烁且不升起。本方案要把灯带扩展为整个解锁流程的状态指示器，以不懂设备的普通人的直觉为最高优先：直观、简洁、一眼看懂"现在轮到我做什么 / 我做对了没 / 完事了没 / 是不是坏了"。

硬件前提（影响全方案）：蓝灯位 PA7 仅为占位（原蓝脚 PA6 已改作 USB_EN，板上尚未接蓝色 LED）， 当前物理可见的颜色只有 红(PA5)、绿(PA4)、黄(红+绿) 三种。 所有用到蓝分量的图样（白/青/紫）均附无蓝灯降级表（见 5.3），并强烈建议先补齐蓝灯硬件（见第 9 节）。

2. 解锁相关流程总览

2.1 流程 A：Locker 结账编排（主业务，非阻塞状态机）

代码：App_Locker.c，主循环 App_Locker_Process() 驱动。上位机下发「硬标签 EPC 清单（m 个）+ 软标数量（N）」后 START 激活：

IDLE 待机→ CONFIGURED 扫描比对→(首匹配) UNLOCK_HOLD 升起保持→(m==n) SOFT_DECODE 软标解码→(N 用尽) DONE 结账完成(5s)→ LOWERING 回降→ IDLE
  • CONFIGURED / UNLOCK_HOLD 中：UHF 连续盘点 → 每读到一张标签与清单比对： 清单内且未解锁 → MATCH_OK（首张立即寻触升起至 KEY_UP）；清单内已解锁 → 静默忽略；清单外 → MISMATCH（红闪 3s，不升起）。
  • SOFT_DECODE：磁块保持升起，等待软标（AM 解码器/红外侧）逐个消耗解码次数，上位机 CONSUME_SOFT 或消磁事件驱动；兜底窗口 5min。
  • 任意运行态：阶段超时 / CANCEL → LOWERING 回降 → IDLE；电机/链路故障 → FAULT（ERR 常亮，CANCEL 可退出）。

2.2 流程 B：OneShot 单标签同步开锁（协议触发，阻塞式）

代码：App_LockerOneShot.c，上位机一条命令发起的"同步"流程，与流程 A 互斥：

PRECHK 前置检查→ UHF_READY→ INVENTORY 盘点比对→(匹配) RISE 升起→ HOLD 保持监控→(移走/消磁/超时) LOWER 回降→ 完成
  • 盘点无标签 / EPC 失配 → 立即回帧结束（NO_TAG / MISMATCH），不升起。
  • HOLD 段期望标签在场持续监控，结束原因：标签移走 / 标签被换 / 消磁完成 / 保持超时 / UHF 失联 / CANCEL。
  • 电机段失败统一走"安全回退至 KEY_DOWN"后上报（`MOTOR_FAULT`/`MOTOR_TIMEOUT`）。

4. 用户视角分析（站在什么都不懂的普通人角度）

4.1 普通用户只想知道五件事

用户的问题对应设备状态现在的回答重要性
"① 设备开着吗、正常吗？"IDLE / 健康RUN 呼吸（已有，够用）高（已有）
"② 现在轮到我做什么？"扫描等待 / 软标等待没有任何提示（P5）最高
"③ 我刚才做的那下，对了吗？"每张标签匹配 / 每次软标消耗无逐次反馈（只有事件上报上位机）高
"④ 全部弄完了？可以走了吗？"DONE 结账完成无本地反馈高
"⑤ 是不是坏了？该找谁？"FAULT / 行程错误ERR 常亮 / 黄闪（可，但语义与 ① 混杂）高（基本有）

结论：缺口集中在 ②③④ — 全部是"引导"类反馈；而 ①⑤ 已有基础。灯语设计的重心是引导，不是罗列内部状态机 phase（那是给维修/上位机的，协议查询已有）。

4.2 简洁性原则（普通人约束）

  • 普通人稳定记忆的灯语上限约 3~4 种颜色语义：绿=好/正常、红=不对/坏了、白(蓝缺降级黄)=正在等下一种动作、灭=没事发生。其余一律用闪烁节奏区分，不用新颜色。
  • 同一时刻只亮一个图样。绝不用"两种颜色各闪各的"表达两个信息——普通人读不出，维修信息走调试通道。
  • 颜色语义必须单调递进：过程中 ≤ 引导色，完成才给绿，错误只给红。绝不在过程中亮绿常亮以外的"奖励色"。
  • 动作性反馈（每成功一张闪一下）时长 ≤300ms，不与稳态引导冲突。

5.2.1 主线时序示例（流程 A 完整结账）

青慢闪·等你放硬标签→ 绿闪×1·这张对了→ 绿常亮·开锁中→ 白常亮·轮到软标→ 白闪×N·逐个完成→ 绿三连闪·结账完成→ 灭·回降复位

失配插曲（任意扫描段）：红快闪 3s → 回到青慢闪，磁块始终不动。

5.4 优先级仲裁（解决 P1/P2）

全部图样收编进唯一的仲裁器，每拍（~10ms）按以下顺序取"当前应显示图样"，直接写 RgbLedHl_Set()：

优先级来源说明
L1行程开关错误（App_Stepper_GetSwitchErr()）保留现有黄/粉红逻辑原样迁入
L2FAULT / 红常亮Locker FAULT 态 + OneShot 电机失败后置位
L3维修/自检一次性（MotorTest 黄闪、POST 彩虹、Homing 黄慢闪）一次性图样自带时限
L5业务稳态（Locker / OneShot 当前状态映射）两流程互斥（前置检查保证），不会竞争
L5.5手动覆盖（FC_RGB_CTRL，仅 IDLE，10s 回收）调试用途
L6OFF（默认）所有来源都无请求时灭

稳态请求以申请—持有方式表达：各流程在状态迁移点调用 App_RgbLedPat_Set(图样ID)，仲裁器只看"当前最高优先级的持有者"。

5.5 一次性闪显（事件叠加）机制

"每匹配一张闪一下绿"这类瞬时确认不能打断稳态引导（青慢闪/白常亮），设计为叠加闪显队列（深度 1）：

  • 事件发生 → 记录 s_flashPat（图样）+ s_flashUntilMs（now+200~900ms，N 连闪按图样时长算）；
  • 闪显窗口内仲裁器优先输出闪显图样，窗口结束自动回落稳态；
  • 新事件在闪显进行中到来 → 覆盖旧闪显重新计时（同类事件高频时表现为连续快闪，恰好是"连续成功"的直观表达）；
  • MISMATCH 的"3s 红闪"也用同一机制（时长 3s），与现状行为一致。

8. 风险与待决策点

#风险/决策点建议
R1蓝灯硬件缺失（P3）：白/青/紫全部不可见，本方案三个核心引导图样都依赖蓝分量两步走：先按降级表上线（绿慢闪/黄慢闪/黄闪，直觉性已够 80%），同时尽快补 PA7 蓝灯硬件，置 RGB_HAS_BLUE=1 后白/青全量生效
D1MISMATCH 时 ERR 灯(PA3) 是否同步红闪：现状 ERR 闪 3s；若 RGB 红闪已足够，ERR 保持灭可把"ERR=设备级故障"语义让干净（修 P4）建议：MISMATCH 只用 RGB 红；FAULT 才 ERR 常亮 + RGB 红常亮。需用户确认（属行为变更）
D2手动设色回收策略：10s 自动回收 vs 仅 IDLE 可设 vs 运行中拒绝建议取"仅 IDLE + 10s 回收"（V9 口径），兼顾调试便利与业务安全
D3Homing 黄慢闪是否保留保留（成本低、增加"开机自检"信心）；若嫌开机灯语过多可与 POST 二选一
R2OneShot 阻塞期间主循环停转：图样推进依赖 one_pump() 加 Tick，漏加则该流程内灯语冻结实施时 one_pump 第一行即 Tick；MotorHoming 阻塞回零同理（回零段直接黄常亮即可，不闪，规避节拍依赖）
R3绿慢闪（降级扫描）与绿常亮（已开锁）仅节奏之差，色弱用户可能误读绿慢闪周期取 1.5s 加大节奏差；补蓝灯后即消（青 vs 绿不同色）
R4闪显队列深度 1：极快连续事件互相覆盖可接受——表现为连续快闪即"连续成功"直觉；不加深队列（保持简单）

9. 相关建议（需求允许范围内）

  • 补齐蓝灯硬件（最优先建议）：PA7 已预留，一颗蓝 LED 即可解锁白/青/紫三色。当前 8 色理论只有红/绿/黄 3 色可见，"等待红外=白色"的需求在硬件补齐前只能以黄/绿降级呈现。
  • 完成提示加一声蜂鸣：结账完成时绿三连闪 + 蜂鸣"滴"一声（板载 PC12 蜂鸣器与 IR 检测逻辑已存在）。对普通人，听觉的"完事了"比任何灯都直观，且不强依赖蓝灯硬件。软标逐个成功如也配轻"嗒"声，收银节奏感极佳。
  • RUN 呼吸灯维持现状：专职"活着"心跳，不参与业务灯语——避免普通人在多个灯之间无所适从（三灯分工：RUN=活着，ERR=坏了，RGB=业务引导）。
  • 灯语表印在设备机身贴纸/说明书：普通人 3 句话讲完——"绿色=正常，红色=不对，白/黄=正在处理中"。硬件无论怎么降级，这三句始终成立。
  • 协议侧零改动：灯语纯本地，全部状态/事件本就经 LOCKER_SUB_QUERY/GET_EVENT 上报，上位机可视化与本地灯语互不依赖，可独立演进。

10. 范围边界（本方案不做的事）

  • 不改动 RgbLedHl 硬件层、不加 PWM 调光（灯带为开关型，呼吸交给 RUN 灯）。
  • 不改动协议帧格式（FC_RGB_CTRL 语义微调仅实现层，帧不变）。
  • 不处理 IR 光电+蜂鸣逻辑（已独立存在）；不处理 Boot 侧 LED（Boot 阶段无 RGB 需求）。
  • 不实现"剩余数量进度条"类花样（单色灯带无像素，闪烁计数普通人读不了；剩余数经上位机/事件查询）。
  • 本轮只出方案不改代码；实施按第 6 节清单另起一轮。
