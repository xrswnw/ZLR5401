3. 方案核心（详见 Plan.html 第 5 节）

主线灯语： 青慢闪·等硬标签 → 绿单闪×1·这张对了 → 绿常亮·开锁中 → 白常亮·轮到软标（红外/消磁） → 白单闪×N·逐个完成 → 绿三连闪·结账完成 → 灭·回降复位。
失配插曲：红快闪 3s 不升起（现有固定逻辑保留）。 故障：红常亮 + ERR 常亮。行程错误：黄/粉红 500ms 闪（现有，最高优先级）。
  • 优先级仲裁器（新模块 App_RgbLed_Pattern）统一输出，解决 F2/F3：行程错误 L1 → 故障 L2 → 维修/自检 L3 → 业务稳态 L5 → 手动覆盖 L5.5 → 灭 L6。
  • 一次性闪显队列（深度 1）叠加在稳态之上，实现"每成功一个闪一下"，不打断引导色。
  • 无蓝灯降级表：白→黄慢闪、青→绿慢闪、POST 蓝步骤跳过，由 RGB_HAS_BLUE 编译开关一键切换，补齐蓝灯硬件后全量生效。

4. 需求点的取舍说明（对 Demand.md 第 3 条的响应）

需求原想法方案采用 / 调整理由
等待红外（软标）显示白色采纳：白常亮（降级黄慢闪）白=红绿蓝全亮，视觉上"纯净的等待"直觉好；蓝灯补齐前用黄慢闪保持可区分
等待硬标签解码全灭调整为青色慢闪（降级绿慢闪），全灭留给"待机/无需关注""等硬标签"是设备最需要引导用户的时刻，全灭会与待机不可区分（F5 类问题），用户不知道该放标签；灭保留给 IDLE/回降这类"无需关注"态
解码成功一个标签闪烁一下采纳：绿单闪 200ms（软标成功为白/黄单闪，消磁失败红双闪）逐次正反馈，叠加机制不打断稳态引导
EPC 扫描中展示采纳：青色 1s 慢闪即"EPC 扫描进行中"，与"等待硬标签"同图样扫描与等待对普通人是同一件事（"在等我放/在读我放的"），一色到底更简洁

6. 相关建议（超出需求的提议）

  • 结账完成加蜂鸣"滴"一声（PC12 蜂鸣器已有）——对普通人听觉确认比灯更直观，且不依赖蓝灯硬件。
  • 三灯分工固定：RUN 呼吸=活着、ERR=坏了、RGB=业务引导，避免多灯歧义。
  • 机身贴纸三句话："绿=正常，红=不对，白/黄=正在处理中"——无论硬件如何降级始终成立。
  • 协议零改动：灯语纯本地，上位机可视化另有 LOCKER_SUB_QUERY/GET_EVENT 通道，互不依赖。
