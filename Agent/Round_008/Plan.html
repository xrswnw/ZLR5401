2. 协议基线（脚本实现依据）

2.1 帧格式

┌──────┬──────┬─────┬─────┬─────────┬──────┬─────────┬─────────┐
│ 0x53 │ 0x77 │ADDR │ 0x00│ length  │ func │ data    │ crc32   │
│  S   │  w   │ 1B  │RSV  │ LE16     │ 1B   │ N bytes  │ LE32    │
└──────┴──────┴─────┴─────┴─────────┴──────┴─────────┴─────────┘
length = 1 + N + 4 (func + data + CRC32), 有效范围 5..1029
响应 func = 请求 func ^ 0xFF
本机 devAddr = 0x01, 广播 = 0xFF

2.2 CRC32（须与固件完全一致）

MPEG-2: poly=0x04C11DB7, init=0xFFFFFFFF, 逐位 MSB, 无反射, 无最终 XOR.   // App_Param.c:8
错误处理: CRC 不符 / length 越界 / reserved≠0x00 → 设备静默丢弃, 不响应.
脚本参考实现：CRC 覆盖 前 (N+7) 字节（header+addr+len+func+data）， 写入帧尾 4B LE。脚本用独立 Python 实现，并用已知数据与固件唯一性自校验（见 A1 测试）。

2.3 传输

USB HID Interrupt, VID:PID=0x5377:0x5378, 报告 ID=0x02, 包长 64B.
收包: 首个字节为报告 ID 0x02, 剥除后剩余 63B 为协议帧.
依赖: 已有 .venv 含 hid/hidapi + pyusb, 无需新增依赖.

4. 分层测试策略

A 协议层(无硬件)→ B 链路否定→ C–J 功能闭环(读→写→回查)→ 破坏性(reset/boot, opt-in)
层目的关键点
A 协议层脚本自身正确性（无需设备）CRC 已知数据、帧编解码 round-trip、响应 func 推导、报告 ID 剥除
B 链路否定失灵帧必须被静默丢弃错 CRC / reserved≠0 / length 越界 / 错地址 / 未知 FC → 断言"无响应"
C–J 功能每条命令参数 · 闭环回查读型直接校验; 写型用 GET/CONFIG/QUERY/事件回查生效
破坏性RESET / ENTER_BOOT 行为opt-in 开关; 复位后枚举重连; ENTER_BOOT 后用 EXIT_BOOT 收尾回归 App

6. 闭环验证策略

  • 读型命令（HANDSHAKE/DEVICE_INFO/QUERY/GET_CONFIG/GET_STATUS/HEALTH/STATS）：直接对响应字段做语义断言（范围、一致性）。
  • 写型命令（MOVE/TEST/SET_CONFIG/CONFIGURE/ADD/…）：由后续读取确认生效——步数变化、状态迁移、配置回读、事件码、计数增量。
  • 否定型：断言"静默"（超时无响应）而非报错，验证设备不崩溃、不误响应。
  • 破坏型：RESET/ENTER_BOOT 后执行枚举重连 + 恢复（EXIT_BOOT），确保链路回到可测状态。
  • 每个用例失败时dump 原始请求/响应对（hex）进报告，便于定位是协议、参数还是固件问题。

9. 参照《App_Protocol.html》的一致性校验点（潜在差异监测）

以下为固件实现 vs 协议文档可能存在出入、需脚本如实记录（先判 INCONCLUSIVE 而非直接 PASS）的点：

点协议文档固件现状（App_Dispatch 观测）
SPEED 范围1~2000未校验范围，直接 SetSpeedHz（G5）→ 记实
TORQUE 范围6~100未校验，直接 SetTorquePercent（G6）→ 记实
TEST passes=0参数非法App_MotorTest_Start 返回（G13）→ 记实

确定是文档错误则标注"建议改文档"；是固件缺失校验则按 §8 进入修码闭环。

11. 风险与建议

  • 破坏性命令时序：RESET/ENTER_BOOT 会中断 USB，脚本须带 枚举重连 + 超时保护；ENTER_BOOT 后必须 EXIT_BOOT 收尾，否则设备停在 Boot。
  • 电机安全：MOVE 用小步数；TEST 依赖真实行程开关，运行前确认机构无阻挡、转矩/时限保护在位。
  • UHF 硬件依赖：INVENTORY/读写/SCAN 需真天线+标签；缺件一律 SKIP 而非 FAIL，报告中注明"未覆盖项"。
  • 协议文档滞后：可能出现"固件行为 ≠ 文档"——脚本先记 INCONCLUSIVE，避免误判固件缺陷；由人工裁定改固件还是改文档。
建议：优先跑 P0–P3（零硬件即可完成协议有效性 + 链路否定 + 只读闭环），把"命令帧/CRC/静默丢弃/响应 func"这层一次性验证到位； P4–P7 硬件项在具备线缆与标签时再开，避免阻塞纯协议验证。
