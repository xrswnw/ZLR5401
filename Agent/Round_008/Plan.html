1. 校验目标与范围

目标：以《常州亚森/约束/Link.txt》的运行逻辑为唯一业务基准，对当前已实现的 App_Locker（开锁器业务编排） + App_UHF（硬标签 EPC） + App_AM（软标解码器） + App_Stepper（升降） 做逐条比对， 审计业务逻辑与状态机管理是否与约束一致、有无漏洞。
范围声明：本轮只做"校对分析 + 生成计划/报告"，不改动任何已实现功能。 所提整改项均为待审阅计划，不自动执行。

被审文件：Application/src/App_Locker.c/.h、App_UHF.c/.h、 App_AM.c/.h、App_Stepper.c、App_MotorTest.c、 App_Dispatch.c、main.c。

2. 约束原义逐条解读（Link.txt 运行逻辑）

#约束原文解读为可校验需求关键参数
R1客户付款 → 上位机把结账标签 EPC 传给开锁器上位机经 USB 下发「硬标签 EPC 清单 + 软标数量」EPC 清单、软标数 N

R6读到不同 EPC 且解锁数量 n 达硬标签数 m（m==n）→ 硬标签解锁结束，进软标hardMatched==hardCount 时进入软标阶段m==n
R7硬标签完成后解锁解码器使用，每个软标对应一次解码数量软标阶段可消耗解码次数softCount / softUsed
R8次数用完后结账完成softUsed==softCount → DONE + 上报softUsed==softCount

3. 实现 ↔ 约束 对照总表

约束实现位置状态说明
R1 上位机下发 EPCFC_LOCKER_CTRL / CONFIGURE+ADD符合CONFIGURE 清空并设软标数，ADD 逐条追加硬 EPC
R2 接收清单App_Locker_Configure / AddTag符合容量 16，ADD 可累积
R3 光电触发UHF Inventory + TagTake (轮询)部分无真光电触发，靠 UHF 缓冲轮询；NotifyTag 为空占位（详见 P2-3）
R4 比对/升降/回传locker_process_configured符合匹配→rise+EVT_MATCH_OK；不匹配→ERR 闪+EVT_MISMATCH
R5 2min+30s*nStart / match 内部分公式对，但匹配时窗口被整体重置（见 P1-2），与"预留给全部标签"语义不一致
R6 m==n 进软标hardMatched>=hardCount符合超标量 > 处理安全
R7 软标解码消耗StopDecode / CONSUME_SOFT部分依赖上位机逐条 0x06 手动消耗，未与 AM 解码器事件联动（见 P2-1）
R8 次数尽结账完成softUsed>=softCount→DONE符合DONE 后 5s 回 IDLE

4. 状态机审计（当前实现字面核对）

4.1 业务状态机 App_Locker

LOCKER_IDLE→CONFIGURE/START→ LOCKER_CONFIGUREDm==n→ LOCKER_SOFT_DECODE次数尽→ LOCKER_DONE→5s→ LOCKER_IDLE
CONFIGURED/SOFT超时/取消→IDLE 任意（链路）FAULT→LOCKER_FAULT→清障→IDLE
状态入口动作本拍处理出口核对
IDLE降磁块 + Err 灭空—注：LOCKER_UNLOCK_HOLD 已定义但恒未用，实际用 CONFIGURED 承载保持态
CONFIGURED上电 UHF+Inventory，设窗口故障→FAULT；UHF 空闲→再 Inventory；TagTake→比对m==n→SOFT；超时→Cancel；FAULT匹配/不匹配各分支齐
SOFT_DECODE解窗口（holdDeadline=0）Err 保持灭超时→Cancel；次数尽→DONE软阶段无主动超时（见 P1-3）
DONE设 5s 回 IDLE 窗口Err 灭5s→Cancel(正常归位)OK
FAULT降磁块 + Err 常亮—ClearFault→IDLEFAULT 仅在 UHF 链路断/ERROR 进入

审计结论：状态集合 {IDLE, CONFIGURED, SOFT_DECODE, DONE, FAULT} 覆盖约束主流程； 但 LOCKER_UNLOCK_HOLD 为死状态（可清理或按设计并入 CONFIGURED，见 P2-5）。

5. 发现的问题与风险（按严重度）

5.1 高（P0）— 与硬约束语义冲突

#问题证据影响
P0-1必备件：离线/清单有效期语义空缺。约束隐含"结账后此窗口内要放好标签"，但无清单到期、关店清空策略（Plan §6.1#9、§6.3#3）CONFIGURED 无到点强制回 IDLE；Cancel 仅指令触发无人值守时清单常驻，安全/业务歧义

5.2 中（P1）— 语义偏差

#问题证据影响
P1-1软标阶段无超时：进入 SOFT_DECODE 已清窗口，若上位机不再消耗，将永久停留locker_process_soft 仅检查 holdDeadline（已被清零）软标阶段失去安全边界
P1-2R5 窗口语义偏差：每次匹配都重置 holdDeadline，等价"每匹配一张 +2min 顺延"，非"预留总时长"locker_process_configured 匹配分支重算 win多标签时总开锁时长超出约束意图
P1-3FAULT 进不了 IDLE：故障后仅 App_Stepper_ClearFault 链路侧，无"恢复后自动/显式回 IDLE"入口被 Locker 使用LOCKER_FAULT 无 process 恢复判定故障态需上位机干预才能恢复
P1-4反作弊缺失（Plan §3.2 重点）：磁块升起后对"当前 EPC 摘换非清单标签"无高频重校验降块配置态只在 TagTake 有且匹配时升，升后不再复核存在"先真标签升起、再偷换"漏洞

5.3 低（P2）— 增强/对齐

#问题证据影响
P2-1软标解码未与 AM 事件联动：软标阶段应"检测到标签→自动消耗一次解码次数"App_AM_GetEventCount 未被业务消费当前只能上位机手动 0x06，不达"自动解锁解码器"
P2-2绿灯/红灯语义由 Locker 手动改，未走 RGB/LED 状态机统一Locker 直接用 LedHl_EOn/EOff多状态指示灯叠置时易乱（关键读卡可再细分）
P2-3光电触发占位：App_Locker_NotifyTag 为空App_Locker.c:183R3 的"光电触发"未真正落地
P2-4清单"重复 EPC"未去重：同一 EPC 两条会被当成两个待解锁项AddTag 不查重罕见但会造成 m 虚高、n 永远差一
P2-5死状态 LOCKER_UNLOCK_HOLD 恒未用 + 注释栈与代码不一致App_Locker.h:41维护成本，非功能故障
P2-6行程测试与业务电机互斥无保护：TEST 运行时 Locker 置于 IDLE，但无封锁main.c 两 Process 顺次并发时电机归属需上层协调（暂可接受）

7. 整改计划（待执行，分 P0/P1/P2）

以下均为计划，需用户审阅后再执行。已实现功能默认不动。

P0 — 必修（与约束安全语义相关）

  1. 清单有效期 / 关店清空：CONFIGURED 增加"到点强制回 IDLE + 上报清单过期事件"；新增上位机"清清单"子命令。 需求确认

P1 — 应修（语义偏差）

  1. 软标阶段超时：进入 SOFT_DECODE 时设软标门槛窗口（如沿用 2min 或新增可配），到点 Cancel。
  2. R5 窗口语义：改为"总窗口固定从 START 起算"，匹配不重置整体窗口（或仅做微步刷新防异常）。 需求确认
  3. FAULT 自恢复：LOCKER_FAULT 增加链路恢复探测，恢复后自动回 IDLE（或经上位机确认）。
  4. 反作弊：磁块升起后维持高频 Inventory，一旦"当前 EPC 不在待解锁/已解锁清单"立即降块 + 上报异常（对齐 Plan §3.2 下降延迟核心指标）。

P2 — 增强/对齐

  1. 软标自动消耗：软标阶段用 App_AM_GetEventCount 增量驱动一次自动解码 + StopDecode，替代仅手动 0x06。
  2. 灯控收敛：把 Locker 的绿/红动作收敛到统一状态指示层，避免多状态互踩。
  3. 光电触发：给 App_Locker_NotifyTag 接真光电/读卡硬件（若硬件已具备）。
  4. EPC 去重 + 查重：ADD 时按 EPC 去重，m 计数用去重后集合。
  5. 清理死状态：删除 LOCKER_UNLOCK_HOLD 或按设计显式并入 CONFIGURED，修正注释。
  6. 电机互斥：MotorTest 运行时 Locker 拒绝 START，或反之加保护。
建议优先级：若现场已稳定交付，优先 P1（语义偏差）+ P0 的"清单过期"； P1-4 反作弊与 P2-1 软标自动化为业务收益最高的两项。
