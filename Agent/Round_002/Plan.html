ZLR5401 · Round_002 主控更换为 GD32F303RC — 迁移实施计划

文档性质：调研 + 实施计划（本计划不执行，待用户审阅确认后方可动工） |  生成日期：2026-08-08  |  Rev2：接入 Sdk/CherryUSB、锁定 HSE 12MHz、新增自动烧录验证流程

一、需求确认

1. 本系统主控更改为 GD32F303RC，使用 STM32 的库，原则上应该兼容，调研下相关配置文件调整等等。保持逻辑不动。

需求要点拆解：

  • 目标器件：GD32F303RC（GigaDevice，STM32F103 的"增强版"），LQFP64 封装。
  • 约束 A：尽量沿用现有 STM32F10x_StdPeriph 库，不整体换用 GD 官方库，最大限度复用代码。
  • 约束 B：业务逻辑（协议、分发、参数、SysTick、看门狗、LED 等"与芯片无关"层）保持不变。
  • 约束 C：仅做与芯片相关的"底层/配置"调整（时钟树、启动、链接脚本、烧录、调试）。
  • 约束 D（Rev2 新增）：USB 底层接入 Sdk/CherryUSB（替代 STM32 PMA USB 库）。
  • 硬件基线（Rev2 确认）：外部晶振 HSE = 12MHz；开发板由用户连好后执行自动烧录 + 验证。

当前架构基线（Round_001 已成型）：App + Boot 双区，USB FS 设备传输 + IAP 握手升级；STM32F10x StdPeriph + STM32 官方 USB 设备库（PMA 架构）；HSE=12MHz，PLLx6=72MHz 主频。

三、兼容性调研结论（本计划核心）

GD32F303 官方定位"STM32F103 寄存器级兼容"，但对当前工程而言是 「部分兼容」，不是即插即用。分三层评估：

3.1 完全/基本兼容（逻辑可原样保留） — 占代码主体

模块评估
GPIO / USART / SPI / I2C / 定时器 / ADC / SysTick / NVIC兼容寄存器地址一致，StdPeriph 驱动可直接编译使用
业务层：Dispatch / CustomProtocol / Param / Iwdg_HL / Led_HL / SysTick_HL / Usb_HL(上层)不变与芯片无关，保持原样
USB 协议逻辑（描述符、类处理、枚举流程的"协议层"）部分复用协议概念可沿用，寄存器 IO 层废弃

注：GD 要求"先开时钟再配外设"，当前代码 RCC 驱动为 StdPeriph，顺序一般正确；个别位定义差异需编译期验证。

3.2 需要改动（与芯片强相关）

#项原因改动范围
1编译器参数 -mcpuM3 → M4，需选软/硬浮点toolchain + 启动文件
2时钟树Cortex-M4 支持 120MHz；PLL 倍频位、USB 48MHz 时钟分频不同；当前 72MHz PLLMul_6 需按新晶振重算App_Sys_CfgClock / Boot 时钟 + CMake HSE_VALUE

4USB 设备底层PMA 架构 → OTG FIFO 架构，寄存器/IP/中断完全不相容接入 Sdk/CherryUSB（dwc2 端口）替代 STM32_USB 库
5启动文件 / 向量表中断向量数量与名称不同（GD F30x 无 USB_LP_CAN 共享向量，改独立 OTG/USBFS IRQ）App/Boot 启动 .s + stm32f10x_it.c
6链接脚本Flash 256K、RAM 48K；App/Boot 分区地址与容量调整App/Boot 的 .ld
7工程宏定义STM32F10X_MD → GD 型号宏；去密度宏改器件宏两个 CMakeLists.txt
8调试/烧录配置device 名、FLASH_SIZE、openocd target、jlink device.vscode/*、flash_*.sh

3.3 「保持逻辑不动」的边界说明（重要，需用户知晓）

结论：业务逻辑（3.1）可完全不动；但 USB 设备底层与 Flash 控制器 HAL 无法"改了配置就兼容"——这两个是 GD32F303RC 与 STM32F103 的核心差异点。USB 底层已确定接入 CherryUSB 解决；Flash HAL 仍需按 GD FMC 重写。因此 "保持逻辑不动" 精确含义：App/Boot 业务逻辑不变，仅芯片相关底层/配置替换。

USB 的"上层逻辑"（协议传输 App_Usb_HL 之上）保持不变；底层驱动从 STM32 PMA 库换成 CherryUSB。

四、实施步骤（默认路径 A：沿用 STM32 库 + 局部适配）

步骤 0 · 备份与变更日志（遵循全局 CLAUDE.md 规则）

  1. 执行 ./backup.sh "Round_002: 主控更换 GD32F303RC" 生成全量快照（当前备份已至 Round_004）。
  2. 确认备份 4 步：快照生成、Changelog 追加、轮转（超 32 层删最旧）、源-目的计数验证。
  3. 任何违规删除一律 mv 至 TrashCan/，不用 rm。

步骤 1 · 编译器与内核切换

修改 toolchain-arm-none-eabi.cmake：

# M3 → M4（默认软浮点，不引入 FPU 依赖，保证逻辑不变、行为稳定）
set(CMAKE_C_FLAGS  "-mcpu=cortex-m4 -mthumb -mfloat-abi=soft -Wall -std=gnu11 -ffreestanding")
set(CMAKE_ASM_FLAGS "-mcpu=cortex-m4 -mthumb -mfloat-abi=soft")

同时 App/Boot 启动文件中 .cpu cortex-m3 改为 cortex-m4、.fpu softvfp 与软浮点一致。

若后续要用 FPU/DSP，可改 -mfloat-abi=hard -mfpu=fpv4-sp-d16 并启用 FPU——但默认不做以贴合"逻辑不动"。

步骤 2 · 时钟树重算（HSE = 12MHz 已确认）

当前：HSE 12MHz × PLL6 = 72MHz。GD32F303RC 最高 120MHz，充分利用性能建议 120MHz，且 12MHz × 10 = 120MHz 是整数倍频、USB 48MHz（120/2.5 或专用分频）可整除，时钟干净：

// 目标 120MHz, HSE=12MHz: 12 × PLL10 = 120MHz
RCC_PLLConfig(RCC_PLLSource_HSE_Div1, RCC_PLLMul_10);

// USB 48MHz：GD F303 OTG 的 48MHz 时钟由专用分频导出（非 F103 的 72MHz/1.5）
// 由 CherryUSB dwc2 初始化的 usbd 时钟树接管配置
  • 改 App_Sys_CfgClock.c 与 Boot 对应时钟文件：PLL 倍频、Flash 等待态（120MHz 的 FMC_WS 数与 Prefetch 语义）、USB 时钟分频。
  • 两个 CMakeLists.txt 的 HSE_VALUE：当前已是 12000000，与 12MHz 晶振一致，无需改动。
  • SystemCoreClock 宏、SysTick 配置（App_SysTick_HL.c 定时基准）需同步到 120MHz。
  • 定案：主频取 120MHz（12MHz×10 整数倍，性能最佳、USB 48MHz 干净）；如想最小改动可退回 72MHz（改 PLLMul_6），默认按 120MHz 实施。

步骤 3 · Flash 控制器（FMC）HAL 重写

当前 Boot_Param_HL.c 用 STM32 的 FLASH->KEYR/CR/AR/SR/ACR 寄存器直接操作。GD32F303 的 Flash 控制器为 FMC，寄存器布局/位定义不同，需改为 GD 模型：

  • 解锁键、擦除（按页/扇区）、编程（半字）、FMC_WS 等待态、Prefetch 使能位均按 GD32F30x 用户手册重写。
  • 该文件为 .ramcode（RAM 中执行），重写后必须保留 RAM 执行属性（IAP 擦写时 Flash 代码不可执行）。
  • App/Boot 时钟配置里引用的 FLASH_SetLatency / FLASH_PrefetchBufferCmd（StdPeriph 封装）对应改为 FMC 等待态设置。

高风险：IAP 升级可靠性依赖此层，需在本步后专项验证擦/写/校验。

步骤 4 · USB 底层接入 CherryUSB（最大工作量）

STM32F103 的 USB Device FS（PMA，RegBase 0x40005C00 / PMA 0x40006000，共享 USB_LP_CAN 中断）在 GD32F303RC 上不复存在。GD F303 采用 USB OTG FS（Synopsys/FIFO 架构，独立 OTG/USBFS 中断）。本步将该底层换为 CherryUSB，上层逻辑保持不动。

4.1 CherryUSB 能力核对（已调研）

  • Sdk/CherryUSB 已在库内（版本 1.6.1），含官方 CMake 接入文件 cherryusb.cmake（勿直接用根目录那个，需看各端口接入样例）。
  • GD32F303 的 OTG FS 走 dwc2 端口（port/dwc2/usb_dc_dwc2.c + usb_glue_gd.c），dwc2 README 明确列支持 GD32F30X。
  • 注意usb_glue_gd.c 顶部有 #error，需按 GD32F303 实际 OTG 寄存器值补全/放开（GCCFG 等），并按 CONFIG_USBDEV_EP_NUM=4 确认端点数限制。
  • 选用 HID 类（class/hid/usbd_hid.c）以匹配现有传输端点规划（EP1 IN / EP2 OUT）。

4.2 工程接入点（保持上层逻辑不动）

  1. 保留 App_Usb_HL.h 对上层暴露的接口签名不变（App_Usb_HL_Init/Connect/Disconnect/Transmit/IsConfigured 等），业务层 App_Usb.c / App_Usb_Transport.c 不动。
  2. 重写 App_Usb_HL.c：内部从"调用 STM32 PMA 库"改为"调用 CherryUSB HID 设备 API"（usbd_hid_*，usbd_initialize 等），把原有 HID 上报/收发逻辑映射到 CherryUSB HID 回调与 API。
  3. 删除/停用 Application/STM32_USB/ 下 PMA 底层（usb_core/regs/int/istr/mem/pwr/init/prop）编译单元，保留可作参考移入 TrashCan。
  4. 在 CMake 中加入 CherryUSB 源（dwc2 + HID class + core）与头文件路径；按 cherryusb_config_template.h 生成 usb_config.h（端点号、包大小、VID/PID 沿用 APP_USB_HL.h 宏）。

4.3 中断与时钟

  • 中断向量：USB_LP_CAN1_RX0_IRQHandler 改为 GD OTG FS 的中断入口（如 USBFS_IRQHandler / OTG 中断），在 stm32f10x_it.c 与启动 .s 同步。
  • USB 48MHz 时钟由 CherryUSB 初始化路径（dwc2 时钟使能）接管，与步骤 2 的 120MHz 时钟树配合。

需专项验证：USB 枚举 48MHz、HID 端点收发、升级通道是否经 USB 传输——接入后 必须先验证（见自动烧录验证步骤）。

步骤 5 · 链接脚本与分区

依据 GD32F303RC（Flash 256K / RAM 48K）重写分区，保留原分区策略与偏移约定：

// Boot（示例，22K 区，具体偏移按原约定保留）
MEMORY {
  FLASH : ORIGIN = 0x08000000, LENGTH = 22K
  PARAM : ORIGIN = 0x08005800, LENGTH = 2K
  RAM   : ORIGIN = 0x20000000, LENGTH = 48K   // 20K→48K
}
// App（示例，FLASH 0x08006000 起，LENGTH 40K→按剩余 232K 起等）
  • App/ld/App_STM32F103C8.ld → 重命名为 App_GD32F303RC.ld；Boot 同理。
  • RAM 由 20K 增至 48K（_estack 需同步上移）。
  • CMakeLists 中链接脚本路径同步。

步骤 6 · 工程宏与启动/中断

  • App/Boot CMakeLists.txt：STM32F10X_MD → GD 型号宏（如 GD32F30X + GD32F303），保留 USE_STDPERIPH_DRIVER。
  • 启动文件若改用 GD 启动模板，则其命名/中断表与 GD 库保持一致；若沿用 STM32 启动文件，仅改 .cpu/FPU 并补 GD 专属中断号。二选一，优先沿用 + 最小改。
  • 确认 StdPeriph 的 stm32f10x.h 与 GD 器件头（gd32f30x.h）二选一作为系统头，避免同名冲突。

决策点③：沿用 STM32F10x 头文件 + 库（推荐，逻辑最小动）还是切换 GD 库头文件？

步骤 8 · 构建验证（含 CherryUSB）

  1. 清空 Build/ 后 ./build_boot.sh && ./build_app.sh，确认无编译/链接错误（含 CherryUSB dwc2/HID 源码编译通过）。
  2. 核对 --print-memory-usage：App/Boot 在 256K/48K 内，关键段（.isr_vector 首 512B）落到预期地址。
  3. ./build_all.sh && ./gen_firmware.sh all 生成合并 HEX，确认分区偏移正确。
  4. 用 size/readelf 检查向量表首项 _estack、复位向量指向正确；确认 OTG/USBFS 中断符号已进入链接产物。

步骤 9 · 自动烧录 + 真机验证（开发板已接好）

开发板已由用户连好，本步的编译 → 烧录 → 验证做成一条自动化流程，减少人工介入。流程载体：脚本（macOS 下 openocd / JLink GDB Server），按以下阶段执行并输出 PASS/FAIL：

9.1 一键烧录脚本：封装 openocd 对 GD32F303RC（256K）的写入

  • flash_all.sh（合并 HEX 全片）与 flash_boot.sh（仅 Boot）改到 F303 目标。
  • openocd_daplink.cfg 用 GD32F30x 目标定义 + FLASH_SIZE 0x40000，SWD 速度按 GD 建议下调。
  • 烧录后 openocd 回读 flash 首区，与源 HEX 比对校验，不一致即 FAIL。

9.2 Boot → App 握手跳转

  • 烧入 Boot + App → 复位 → openocd/GDB 读 PC 与栈指针，确认已跳入 App（_estack 与 App 复位向量命中）。
  • 核对 SCB->VTOR 指向 App 基址。

9.3 USB 枚举验证（验证 CherryUSB dwc2）

  • 主机侧用 system_profiler SPUSBDataType（macOS）或 lsusb 检查设备枚举，VID/PID 应为 0x5377:0x5378。
  • 若升级走 USB HID，则跑一次 HID 读写回环，确认 48MHz 时钟与端点收发正确。

9.4 IAP 升验（验证 FMC HAL）

  • 走升级协议：擦页 → 写 → 校验 → 复位，核验新固件运行，必要时读 Flash 关键区比对。

9.5 其余外设

  • SysTick/看门狗/LED PWM 在 120MHz 下定时正确；I/O（PB5 LED 等）行为与旧板一致。

自动化能覆盖的（烧录、枚举、握手跳转、IAP 校验）尽量一键完成并输出 PASS/FAIL；无法自动判定的（如 LED 肉眼观察、示波器量测 USB 波形）明示为"待硬件人工确认"。验证失败即从备份全量回滚（规则 6）。

五、实现策略（已确定，仅一条主线）

  • 主路径（已定）：沿用 STM32F10x_StdPeriph 库 + STM32F10x 头文件；业务逻辑全保留。
    - Flash HAL 按 GD FMC 重写（[Boot_Param_HL.c](Bootloader/src/Boot_Param_HL.c) + 时钟等待态）；
    - USB 底层接入 Sdk/CherryUSB（dwc2 + HID），替换 [STM32_USB/](Application/STM32_USB/)；
    - 改时钟（12MHz→120MHz）、宏、链接、调试/烧录。
    逻辑 100% 不动  代价Flash HAL 手写 + CherryUSB 工程接入两处重点工作量。
  • 否决项（不采用）：整体迁移 GD 官方 GD32F30x_Firmware_Library——违背"使用 STM32 库"与"保持逻辑不动"，仅当主路径 USB 接入失败时才回退考虑。

六、风险与缓解

风险等级缓解
CherryUSB dwc2 GD glue 需按 F303 补全（#error 未放开、EP 数=4 限制）中按 GD32F303 OTG 寄存器补 GCCFG 等；EPnum=4 下规划好 IN/OUT 端点
USB 上层 HID 收发语义映射到 CherryUSB HID API 出错中仅重写 App_Usb_HL.c，接口签名不变；USB 枚举+收发专项验证
FMC Flash HAL 误写导致 IAP 损坏高按 GD 手册逐寄存器核对；擦/写/校验分步验证；保留 RAM 执行属性 + 自动回滚
120MHz 下 FMC_WS/预取配置错误 → Flash 读异常中按 GD 数据手册设正确 FMC_WS；自动验证稳定性
头文件/宏冲突（STM32 vs GD）中系统头二选一（STM32F10x），避免混入
中断向量不同步 → USB 中断不触发中启动 .s 与 it.c 同步更新 OTG/USBFS 中断名
真机验证失败 / USB 无法枚举中自动烧录脚本输出 PASS/FAIL；失败按规则 6 全量回滚
