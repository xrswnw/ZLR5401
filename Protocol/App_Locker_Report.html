一、约束 → 功能设计映射

《约束/Link.txt》定义了开锁器完整运行逻辑。本设计将其拆分为一个可执行的状态机，逐条落到对已实现底层模块的调用：

#约束原文（Link.txt）实现落点模块
1客户付款上位机侧；设备收到「结账任务」即开始协议层
2上位机把结账标签的 EPC 传给开锁器LOCKER_SUB_ADD 逐条下发硬标签 EPC + LOCKER_SUB_CONFIGURE 设软标数量App_Locker
3开锁器接收硬标签 EPC 和软标数量清单缓存于 AppLockerCtx_tApp_Locker
4客户把标签放到开锁器上，光电触发ONE_SHOT (0x08) v2.3 起光电 PC4 硬门控：放标触发（高电平 200ms 去抖）后才开始 EPC 校对，窗内未触发回 NO_IR；业务状态机路径仍以 UHF 盘点轮询替代（数据面环形缓冲）App_LockerOneShot / App_UHF
5比对 EPC：一致亮绿灯升起开锁；不一致红灯闪烁不升起；结果回传上位机LockMatch 分支 → rise_lock() + 事件 MATCH_OK / MISMATCH 入上报缓冲App_Locker + LED + Stepper

8每个软标对应一次解码数量，次数用尽结账完成LOCKER_SUB_CONSUME_SOFT 消耗一次；softUsed==softCount → DONEApp_Locker + App_AM

二、已实现模块的复用（不重复造轮子）

硬标签 — UHF 读卡 已提供

App_UHF 控制面/数据面解耦：App_UHF_Inventory() 发起盘点，标签结果经 App_UHF_TagTake() 一条条取出（含 EPC + RSSI）。配置/上电由 App_UHF_Open() 完成并持久化。

开锁器业务仅需在 LockConfigured 态轮询数据面，把取到的 EPC 与清单比对——无需触碰 USART1/0xBB 帧底层。

软标 — AM 解码器 已提供

App_AM 提供解码器配置（阈值/命中次数/频率范围/模式）+ 逐命令同步读写的控制面。软标「按次数解码」由业务层按 1 次/软标 的计数驱动。

初版以 LOCKER_SUB_CONSUME_SOFT 显式上报「解码一次」完成计数；后续可改为调用 App_AM_Query() 自动判定解码成功。

升降开锁 — 步进电机 已提供

App_Stepper 提供 App_Stepper_Move()（方向 + 目标微步数）驱动 DRV8434S。本设计以「升起/下降」两个定步数动作封装 rise_lock() / lower_lock()，步数可配置。

状态指示 — LED 已提供

v2.2 已接 LedHl_EOn/EOff 驱动 ERR 通道：FAULT 常亮，正常运行熄灭。MISMATCH 红闪已迁移至 RGB 三色灯带（RGBFLASH_MISMATCH_3S，500ms 周期 / 250ms 亮窗，节奏与旧时间片方案一致；Round_010 起 ERR 灯专职设备级故障常亮）；结账完成保留 300ms 蜂鸣提示。

三、业务状态机（App_Locker · v2.2 重构）

v2.2 重构 对照六条约束逐项审计后重构：磁块升降改为 KEY_UP/KEY_DOWN 行程开关寻触（非阻塞节拍子状态机，与 App_MotorHoming/App_LockerOneShot 同判据），新增 UNLOCK_HOLD / LOWERING 两状态与 FAULT 的 CANCEL 出口；已解锁标签重复读不误报、START 后清单只读、超时窗口回绕安全比较。

stateDiagram-v2 [*] --> IDLE IDLE --> CONFIGURED: START 开扫 (CONFIGURE/ADD 建清单后) CONFIGURED --> UNLOCK_HOLD: 首次匹配 (MATCH_OK, 寻触升起) CONFIGURED --> CONFIGURED: 后续匹配 / 非清单 MISMATCH CONFIGURED --> SOFT_DECODE: hardMatched==hardCount (HARD_DONE) UNLOCK_HOLD --> SOFT_DECODE: hardMatched==hardCount (HARD_DONE) UNLOCK_HOLD --> LOWERING: 超时 TIMEOUT / CANCEL CONFIGURED --> LOWERING: 超时 TIMEOUT / CANCEL (已升起时) SOFT_DECODE --> SOFT_DECODE: 消耗一次软标 (SOFT_USED) SOFT_DECODE --> DONE: softUsed==softCount (DONE) SOFT_DECODE --> LOWERING: 超时 TIMEOUT / CANCEL DONE --> LOWERING: 停留 5s 后回降 LOWERING --> IDLE: 寻触 KEY_DOWN 到位 IDLE --> FAULT: 电机/链路故障 CONFIGURED --> FAULT: 电机/链路故障 SOFT_DECODE --> FAULT: 电机/链路故障 DONE --> FAULT: 电机/链路故障 LOWERING --> FAULT: 回降寻触失败 FAULT --> LOWERING: CANCEL (磁块在空中则先回降) FAULT --> IDLE: CANCEL (磁块在底部) IDLE --> SOFT_DECODE: START 纯软标任务 (hardCount=0 直入)
状态语义：IDLE=空闲锁定 · CONFIGURED=可开锁（硬标比对中） · UNLOCK_HOLD=已匹配升起保持，继续比对剩余硬标 · SOFT_DECODE=硬标已全部解锁，软标计数中 · DONE=结账完成（5s 后回降） · FAULT=故障（ERR 常亮，CANCEL 可退） · LOWERING=回降寻触中。

时间窗计算（约束 #6）

开锁保持窗口 = 2min + (hardCount − 1) × 30s，匹配任一硬标签即刷新该窗口； 窗口内允许重复开锁/取放，超时则磁块回落并上报 LOCKER_EVT_TIMEOUT； 软标阶段另有 5min 兜底窗口（磁块保持升起直至 DONE 回降）。

四、协议扩展 — FC_LOCKER_CTRL (0x0D)

在既有 Sw 帧（CRC32 / HID 报告 ID 0x02）之上新增命令，遵循已有 data[0]=子命令, data[1]=err 风格，响应 func = 0x0D ^ 0xFF = 0xF2。

子命令Host→Device说明

ADD 0x02[cmd, epcLen, epc…]追加一条硬标签 EPC（可连续发，条数 ≤16）
START 0x03[cmd]UHF 上电 + 开扫，进入可开锁
CANCEL 0x04[cmd]取消任务，磁块回落回 IDLE
QUERY 0x05[cmd][cmd,err,state,hm(2), sc(2),su(2), faultReason] 查询状态/计数；faultReason 为最近一次 FAULT 原因诊断码（v2.2 新增：1=UHF链路 2=未回零 3=seek启动失败 4~6=升寻触失败 7=回降寻触失败 8=回降启动失败）
CONSUME_SOFT 0x06[cmd]软标解码 1 次（进 SOFT 后使用）
GET_EVENT 0x07[cmd]取一条上报事件（结果/异常回传上位机）

五、单命令同步开锁 — LOCKER_SUB_ONE_SHOT (0x08)

v2 核心增补：用户视角一条指令携带 UHF 参数 + 期望标签 + 消磁数，设备自行解析并同步阻塞执行完整流程，完成或失败回一帧（含详细失败码 + 诊断字段）。实现：App_LockerOneShot.c。v2.3 语义更新（2026-09-02）：前置加光电 PC4 门控（等客户放标）；初始盘点升级为持续校对（多轮重试抗单轮漏读）；demagCnt=0 时保持期以 EPC 稳定确认（连续在场 3s）为正常完成判据，不再等窗满。

消磁流程 demagCnt 语义

demagCnt = 0（缺省）→ 跳过消磁流程：完全不触碰 AM 解码器；保持期以 EPC 稳定确认为正常完成判据——标签连续在场 3s（ONE_STABLE_CONFIRM_MS）即 endReason=7 STABLE_OK 结账成功；中途离场（3s 防抖窗内未见）重置累计；窗满未确认则 HOLD_TIMEOUT 兜底。 demagCnt > 0：前置阶段对 AM 探链（0x63 总查询）并确保消磁模式（mode=0）；保持期经泵循环推进 App_AM_Process， 监听 cmd17 成功消磁事件（见 §六），本流程内成功消磁事件数 ≥ demagCnt 即回降，endReason=5，demagDone 回传实际完成数。

五.5 CANCEL 打断（安全回降保证）

流程中下发 LOCKER_SUB_CANCEL: 立即回 OK (~80ms) + 置 s_abort 打断标志
前置/光电等待/持续校对阶段: 磁块未动 → 直接以 endReason=6 ABORTED 回帧
升起段被打断: 免疫回退 (s_retreatImmune) 下行寻触 KEY_DOWN → ABORTED 回帧
保持期被打断: 与其他结束原因同级, 走正常回降段
回降段/失败安全回退段: 打断免疫 — 安全动作必须完成, 不接受二次打断
0x08 挂起回帧: err=OK, endReason=6 ABORTED, rise/lower 步数原样回传

六、AM 消磁结果判定（cmd17 突发分类）与计数

live 实测 2026-08-29 直连串口换标签测试实锤了 cmd17 的完整语义，据此重设计了 App_AM.c 的分类状态机：

cmd17 实测语义

场景上报模式结论
测试标签（不可消磁）在场持续连发 FF FF FF FF FF 00 00，≈800ms 周期（实测 29 帧跨 23s 不停）；拿走再回场仍持续连发失败重试
正常标签消磁成功恰好 1 帧后永久静默；拿走再入场不再上报（已消磁标签不再被设备识别）成功
模式循环重触发（0→1→0）对在场已消磁标签无任何新上报消磁只在标签新检测沿触发
关键结论：成功帧与失败帧内容完全相同（帧体恒 2A A2 17 01 01 07 FF×5 00 00 1B，datalen=7），内容无信息，唯一判据是突发模式。修正了旧实现"非 FF 字段=成功"的判定——该分支永远不会触发。

新分类状态机

事件划分：相邻 cmd17 帧间隔 > AM_BURST_GAP_MS = 3000ms（实测帧距 0.8~1.4s，3s 为安全窗）= 新消磁事件
事件结算（静默超 3s 时）：帧数 == 1 → 成功 deactCount++ ；≥ 2 → 失败 failCount++
结算后状态保持（供 GET_STATUS 轮询捕获），下一事件首帧时回到 IDLE

同时修复旧版致命 bug：原 300ms 突发复位窗 < 800ms 实际帧距，连发计数永远无法累积到阈值 3，失败判定从未生效过。

AM_SUB_GET_STATUS 响应（扩展为 19B，向后兼容追加）

字段偏移说明
cmd00x06（无 err 字段）
link10=正常 / 1=超时掉线 / 2=CRC错
evt2..5cmd17 帧累计（LE 32）
